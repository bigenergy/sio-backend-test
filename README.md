# Расчёт цены продукта и проведение оплаты

Symfony 6.4 · PHP 8.3 · PostgreSQL 16 · Doctrine ORM · PHPUnit · PHPStan level 8

Реализация тестового задания; исходный текст задания сохранён в конце файла.

## Что изменилось после ревью

- `Makefile` был сломан — команда `awk` в цели `help` разорвалась переносом строки, и `make` не разбирал файл целиком. Починено; проверяется прогоном `make -n`.
- Оркестрация уехала из контроллера в `PriceQuoteService` и `PurchaseService`. В контроллере остался HTTP.
- `assert()` заменён на настоящие проверки: репозитории отдают сущность или кидают доменное исключение, которое работает и в проде.
- `Money` стал полноценным value object с `plus / minus / percentage`; центы больше не текут по коду.
- Проверки полей выстроены через `Assert\Sequentially`: одна ошибка на поле и никаких лишних запросов в БД.
- Ставки налога переехали из enum в таблицу `tax_rate`.
- У купона два отдельных столбца вместо одного общего, так что дробный процент (7.5 %) теперь выражается.
- `AutowireIterator` заменён на `AutowireLocator` с `#[AsTaggedItem]` — создаётся только запрошенный процессор.
- Добавлены PHPStan (level 8) и PHP-CS-Fixer (`@Symfony`), оба проходят без замечаний.
- Дерево `src/` приведено к одной схеме — по роли.

## Запуск

```bash
make init
```

Цель поднимает контейнеры, ставит зависимости, применяет миграции, заливает продукты,
купоны и ставки налога и открывает bash внутри контейнера. Приложение слушает
<http://localhost:8337>, PostgreSQL проброшен на порт 5433.

Контейнер рассчитан на Linux и macOS; под Windows нужен WSL.

```bash
make up        # запустить контейнеры
make db        # миграции + сиды
make test      # подготовить тестовую БД и прогнать PHPUnit

```

### `POST /purchase`

Тело то же плюс `paymentProcessor` (`paypal` или `stripe`). При успехе возвращает тот же
расчёт с полями `status: "paid"` и `paymentProcessor`. Оплата проводится через
`PaypalPaymentProcessor::pay()` и `StripePaymentProcessor::processPayment()` — классы из
`systemeio/test-for-candidates` используются как есть.

Полный набор примеров, включая все виды ошибок, — в `requests.http`.

## Как считается цена

Купон применяется к цене продукта, налог начисляется на остаток — этот порядок задан
примером из задания: 100 EUR − 6 % = 94 EUR, 94 EUR + 24 % = 116.56 EUR.

Вся арифметика идёт в целых центах внутри `Money`; в евро сумма переводится один раз,
на выходе из контроллера.

| Страна | Префикс | Формат налогового номера | Ставка |
|---|---|---|---|
| Германия | DE | `DE` + 9 цифр | 19 % |
| Италия | IT | `IT` + 11 цифр | 22 % |
| Франция | FR | `FR` + 2 буквы + 9 цифр | 20 % |
| Греция | GR | `GR` + 9 цифр | 24 % |

Формат номера — правило разбора, он остался в `Country`. Сама ставка лежит в таблице
`tax_rate` и меняется без релиза.

Купоны сидируются с говорящими кодами: `P6`, `P10`, `P100`, `P7H` — процент скидки
(`P7H` это 7.5 %), `D15`, `D5` — фиксированная скидка в евро. Купон, которого нет в базе,
отклоняется.

Продукты: `1` — Iphone (100 EUR), `2` — Наушники (20 EUR), `3` — Чехол (10 EUR).

## Формат ошибок

Один формат на все случаи:

```json
{
  "message": "The request is invalid.",
  "errors": [{ "field": "taxNumber", "message": "The tax number ... does not match ..." }]
}
```

`422` — данные не прошли валидацию или процессор отклонил оплату, `400` — тело запроса
не удалось разобрать. Непредвиденные исключения намеренно не перехватываются, чтобы
настоящая ошибка не превращалась в аккуратный ответ API.

## Как добавить платёжный процессор

Один класс:

```php
#[AsTaggedItem('klarna')]
final class KlarnaPaymentAdapter implements PaymentProcessorInterface
{
    public function pay(Money $amount): void { /* ... */ }
}
```

Больше ничего менять не нужно: интерфейс помечен `#[AutoconfigureTag]`, поэтому реализация
сама попадает в локатор `PaymentProcessorRegistry`, а валидация поля `paymentProcessor`
начинает принимать новое имя и упоминать его в сообщении об ошибке.

## Качество кода

```bash
make test   # 72 теста
make lint   # PHPStan level 8 + PHP-CS-Fixer @Symfony
```

Тесты закрывают расчёт цены и купонов, арифметику `Money`, разбор налоговых номеров, оба
адаптера, реестр процессоров, сервис расчёта и оба эндпоинта целиком — через HTTP и
настоящую БД.

Адаптеры проверяются на реальных vendor-классах ровно на их порогах отказа: Stripe не
принимает меньше 100 EUR, поэтому `pay(10000)` обязан пройти, а `pay(9999)` — упасть.
Такой тест сломается, если сумма когда-нибудь приедет к процессору не в тех единицах.

## Принятые решения и рассмотренные альтернативы

**Деньги — целые центы внутри `Money`.** `PaypalPaymentProcessor::pay()` сам принимает
наименьшую единицу валюты, а float в денежной арифметике накапливает ошибку округления.
Рассматривал `decimal` через BCMath — для двух арифметических действий это лишний вес.

**Два процессора расходятся сразу по двум осям:** Paypal берёт центы и бросает исключение,
Stripe берёт евро и возвращает `false`. Поэтому у каждого свой адаптер к общему интерфейсу,
а не `match` в фабрике: при `match` добавление процессора правит существующий код.

**Локатор, а не итератор.** `AutowireIterator` создавал бы все процессоры на каждый запрос,
хотя нужен один; `AutowireLocator` создаёт только запрошенный, а имена для сообщения об
ошибке берутся из `getProvidedServices()`.

**Ставка налога — в базе, формат номера — в коде.** Ставки меняются по решению государства,
это данные. Формат налогового номера — правило разбора, оно фиксировано страной. Следующим
шагом к ставке добавилось бы поле «действует с», чтобы пересчитывать задним числом.

**У купона по столбцу на тип.** Общий столбец, смысл которого зависит от типа, не позволял
выразить дробный процент и читался хуже. Конструкторы `Coupon::fixed()` и
`Coupon::percentage()` не дают создать несогласованную запись.

**Существование продукта, купона и процессора проверяется констрейнтами** — задание просит
валидацию через Symfony Validator. Сервисы проверяют повторно и кидают доменные исключения:
между валидацией и использованием сущность может исчезнуть, а сервис должен держаться и
при вызове не из контроллера.

**Клиенту возвращается обобщённая причина отказа оплаты,** а формулировка процессора
(с номером транзакции и внутренним кодом) уходит в лог.

**Суммы сериализуются с `JSON_PRESERVE_ZERO_FRACTION`,** чтобы цена всегда читалась
одинаково: `124.0`, а не `124` рядом с `116.56`.

**`var/` вынесен в именованный том.** Bind-mount под Docker Desktop на Windows ломает
`cache:clear`, а на Linux и macOS это ещё и заметно быстрее.

**Заказы не сохраняются** — задание не просит истории покупок. Понадобится — добавится
сущность `Order`, которую пишет `/purchase` после успешной оплаты.

**Слоёв ровно столько, сколько нужно:** контроллер → сервис → репозиторий. Никаких
onion/DDD/CQS — задание прямо просит обратного.

# Исходное задание

# Написать Symfony REST-приложение для расчета цены продукта и проведения оплаты

Необходимо реализовать 2 эндпоинта:
1. POST: для расчёта цены

http://127.0.0.1:8337/calculate-price

Пример JSON тела запроса:
```
{
    "product": 1,
    "taxNumber": "DE123456789",
    "couponCode": "D15"
}
```
2. POST: для осуществления покупки

http://127.0.0.1:8337/purchase

Пример JSON тела запроса:
```
{
    "product": 1,
    "taxNumber": "IT12345678900",
    "couponCode": "D15",
    "paymentProcessor": "paypal"
}
```

При успешном выполнении запроса следует возвращать HTTP ответ с кодом 200.

При неверных входных данных или ошибках оплаты следует возвращать HTTP ответ с кодом 400 (или 422), содержащий JSON объект с описанием ошибок.

## Продукты
Продукты предполагается хранить в БД. В качестве примера можно использовать 3 продукта:
- Iphone (100 евро)
- Наушники (20 евро)
- Чехол (10 евро)

## Купоны
Купоны позволяют применить скидку к покупке и могут быть двух типов:
- фиксированная сумма скидки
- процент от суммы покупки

Предполагается, что купоны создаются продавцом и хранятся в системе. Например, при наличии купонов P10 (скидка 10%) и P100 (скидка 100%) покупатель не должен иметь возможности применить несуществующий купон P50.

Формат кода купона вы можете выбрать на своё усмотрение.

## Расчет налога
Налог рассчитывается исходя из страны налогового номера и прибавляется к цене продукта:
- Германия - 19%
- Италия - 22%
- Франция - 20%
- Греция - 24%

Например, цена Iphone для покупателя из Греции составит 124 евро (100 евро + налог 24%). Если у покупателя есть купон на 6% скидку, то цена будет 116.56 евро (100 евро - 6% скидка + налог 24%).

## Формат налогового номера
Форматы налоговых номеров для разных стран:
- DEXXXXXXXXX - Германия
- ITXXXXXXXXXXX - Италия
- GRXXXXXXXXX - Греция
- FRYYXXXXXXXXX - Франция

где X - любая цифра от 0 до 9, Y - любая буква. Длина налогового номера различается в зависимости от страны.

## Детали выполнения
При выполнении задания необходимо:
- реализовать валидацию всех полей запроса, включая корректность налогового номера, используя Symfony Validator
- рассчитать итоговую цену с учетом купона (если применим) и налога
- использовать `PaypalPaymentProcessor::pay()` или `StripePaymentProcessor::processPayment()` для проведения платежа. Эти классы представлены в компоненте `systemeio/test-for-candidates` и не должны модифицироваться.
- обновить `requests.http`, демонстрируя логику работы вашего приложения.

CRUD для сущностей предполагается уже реализованным, дополнительные проверки в сервисах не требуются.
